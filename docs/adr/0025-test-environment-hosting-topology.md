# 测试环境采用 Pages、Render 和 Supabase 托管

SparkBee 使用一套长期存在、团队共享的测试环境，发布来源固定为 `develop`。Vite 前端部署到 Cloudflare Pages，并通过显式 API 基础地址直接访问 Render；Node.js 后端部署为单个 Render 免费实例，以符合桩实例 Actor、OCPP WebSocket 和 SSE 均属于当前进程的架构；PostgreSQL 使用 Supabase 免费套餐，日常发布保留已有测试数据。

测试环境以免费套餐为硬约束，不承诺后端 24 小时在线。独立的 Cloudflare Worker 每 14 分钟访问 Render 的 `/api/health`，以 best effort（尽力而为）的测试环境保活探测降低空闲休眠概率；Cron 调度、公网请求或 Render 平台仍可能失败或延迟，因此这不是可用性保证。保活探测不访问会查询 Supabase 的 `/api/ready`。

前端第一版不识别或包装 Render 冷启动，不增加“服务正在唤醒”状态、就绪轮询或自动重试。首次访问在后端唤醒期间可能显示普通网络错误，测试人员通过稍后刷新页面重试。

测试数据不承担生产级灾难恢复目标。正常发布不得自动清空数据库，但平台故障、误操作或公开 API 滥用导致数据丢失时，可以从空数据库重新执行迁移并重建测试数据；第一版不要求逐次备份或恢复演练。

Render 后端与 Supabase 数据库统一选择新加坡区域，以减少服务端数据库访问延迟；Cloudflare Pages 继续通过全球边缘节点分发静态前端。

第一版使用 Cloudflare Pages 的 `pages.dev` 地址和 Render 的 `onrender.com` 地址，不绑定自定义域名。前端构建时使用稳定的 Render 地址作为 API 基础地址，后端 CORS 精确允许 Pages 的正式测试环境地址。

`develop` 更新通过类型检查、测试和构建后自动发布。功能与发布配置在 `feature/*` 分支开发，合入 `develop` 后才进入测试环境；`release/*` 不作为日常测试环境的部署来源。GitHub Actions 是应用发布的唯一编排器，Cloudflare Pages 与 Render 不再各自独立监听 Git 自动发布。测试环境保活 Worker 作为独立资源手动部署一次，不纳入日常测试环境发布工作流。

`develop` 禁止直接推送，所有改动必须通过 Pull Request 合入，并将类型检查、测试和构建配置为必需检查。合并成功后产生的 `develop` push 才能进入测试环境发布工作流。

`feature/*` 和 Pull Request 只运行质量检查，不创建可访问的预览环境。第一版只维护 `develop` 对应的一套共享测试环境，避免预览前端共享测试数据库或为每个分支复制 Render 与 Supabase 资源。

Cloudflare Pages、Render 和 GitHub Actions 的非敏感配置随代码纳入版本控制，平台控制台只保存秘密和无法声明式管理的资源标识。仓库同时记录所需环境变量名称和环境重建步骤；数据库密码、API Token 和部署 Hook 等秘密不得提交。

数据库迁移在后端发布前执行，迁移失败阻止发布；破坏性数据库变更必须拆成兼容的多次发布。前后端使用独立来源，后端 CORS 只允许测试环境前端来源，不为 `/api` 和 SSE 增加 Pages 代理层。Cloudflare、Render 和 Supabase 的发布凭据保存在 GitHub Actions Secrets，不提交到仓库。

同一时间只允许一个测试环境发布进入数据库迁移和平台部署阶段。较新的提交可以取消仍处于质量检查阶段的过时工作流，但不能中断已经开始迁移或部署的工作流；后续发布排队等待当前发布成功或完成应用回滚。

第一版只使用 GitHub Actions 工作流状态、提交检查和 GitHub 自带失败邮件作为发布通知。工作流 Summary 必须列出数据库迁移、Render 部署、Cloudflare Pages 部署和冒烟测试结果，并提供测试环境地址；暂不接入外部消息渠道。

发布成功不仅要求服务进程存活，还要求后端通过独立的就绪检查连接 Supabase，并在发布后通过桩实例列表 API 和前端 `/charging-points` 页面的只读冒烟测试。进程存活检查与依赖就绪检查保持分离，避免数据库不可用时仍把环境标记为可用。

发布后冒烟测试失败时回滚应用版本，但不自动执行数据库反向迁移。后端失败时恢复上一版 Render 部署并停止前端发布；前端失败时恢复上一版 Pages 部署。数据库迁移必须保持向后兼容，使上一版后端能够继续运行在已迁移的 schema 上。

测试环境第一版不持久化桩实例运行日志。Render 实例重启或重新发布后，本地 JSON Lines 日志可以丢失；需要跨发布排查的问题在复现期间收集，后续再根据实际需求引入持久磁盘或外部日志服务。

Render 发布会终止当前进程内的桩实例 Actor、OCPP WebSocket 和 SSE 连接。第一版接受所有运行中的桩实例在发布时断开，发布完成后由测试人员手工重新启动；不在本次部署工作中引入运行意图持久化或自动恢复。

测试环境第一版公开访问，不实现用户登录或 API 鉴权。CORS 仍限制为测试环境前端来源，但它只约束浏览器跨来源访问，不构成后端安全边界；任何能够直接访问 Render API 的调用方都可能创建桩实例、连接 CSMS 或触发运行操作，这是当前阶段明确接受的风险。

测试环境第一版不承诺固定出口 IP，只连接不要求来源 IP 白名单的 CSMS。如果后续目标 CSMS 强制配置白名单，必须先重新评估 Render 的稳定出口地址与套餐能力。

该方案用托管服务降低第一套共享测试环境的运维成本，代价是后端暂不支持水平扩容，且发布流程必须显式处理跨来源访问、数据库迁移顺序和服务健康验证。
